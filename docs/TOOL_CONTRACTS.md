Tool Contracts

GCP Observability Investigation Agent

Status: Design Draft
Version: 0.3
Derived From: PRD v0.8, DOMAIN_MODEL.md, SYSTEM_ARCHITECTURE.md
Purpose: Define the explicit contracts crossing the LLM, application, investigation domain, and telemetry-provider boundaries.

Purpose

This document defines the tool contracts used by the GCP Observability Investigation Agent.

The contracts specify:

available investigation tools;

request schemas;

result schemas;

validation rules;

error semantics;

telemetry query semantics;

context-protection behavior;

evidence/provenance requirements;

provider-independent boundaries.

The contracts are intentionally independent of:

SQLite schema;

SQL syntax;

GCP SDK classes;

REST request objects;

LLM vendor-specific function-calling formats;

Streamlit.

The LLM communicates through these contracts. Application code validates and executes them.

Contract Design Principles

3.1 Structured Only

Tool arguments must be structured data.

Free-form executable query languages are not permitted.

3.2 Provider Neutrality

The tool contract represents observability concepts rather than the implementation of a specific monitoring backend.

3.3 Validate Before Execute

Every request passes through deterministic schema and policy validation before any provider operation is executed.

3.4 Explicit Results

Success, empty results, invalid requests, policy rejection, and provider failures must remain distinguishable.

3.5 Evidence Traceability

Returned observations must preserve enough provenance to identify the underlying metric, resource, time range, and query operation.

3.6 Bounded Results

Tools must never return unbounded payloads to the LLM.

3.7 No Silent Approximation

Unsupported query semantics must return explicit errors or warnings rather than silently changing the user's request.

Common Types

4.1 ProjectId

string

Represents the monitoring scope/project.

4.2 MetricType

string

The canonical metric identifier.

A human-friendly metric name must not be assumed to equal its canonical metric type.

4.3 ResourceType

string

The monitored-resource type.

4.4 MetricLabels

map<string, scalar>

Labels belonging to the metric.

4.5 ResourceLabels

map<string, scalar>

Labels belonging to the monitored resource.

Metric labels and resource labels are separate namespaces.

4.6 TimeInterval

TimeInterval
├── start_time
└── end_time

Both timestamps are explicit and normalized before provider execution.

4.7 AlignmentPeriod

Duration used to align observations within individual time series.

Examples:

1m
5m
15m
1h
1d

The supported set is provider/metric dependent.

4.8 PerSeriesAligner

Represents an operation applied independently to each time series during alignment.

Only supported operations may be used.

4.9 CrossSeriesReducer

Represents the operation used to combine multiple aligned time series.

Examples may include:

REDUCE_NONE
REDUCE_MEAN
REDUCE_MAX
REDUCE_MIN
REDUCE_SUM

Only supported reducers may be executed.

4.10 GroupByField

Identifies a supported dimension used to group time series before cross-series reduction.

4.11 ResultMetadata

Describes whether returned data is complete and whether transformations were applied.

Conceptually:

ResultMetadata
├── returned_count
├── total_count_known
├── truncated
├── transformed
└── transformation_summary

4.12 EvidenceId

A stable identifier for an investigation-facing observation or deterministic analysis.

Examples:

obs-001
obs-002
analysis-003

The identifier must be generated by the application, not invented by the LLM, and must be unique within the investigation.

These identifiers are the references the LLM may use when proposing findings or hypotheses.

Common Tool Request Envelope

Every tool call should be representable as:

{
"request_id": "uuid",
"tool_name": "query_metric",
"arguments": {}
}

Fields

request_id

Unique identifier for the attempted tool call.

tool_name

Must match a registered tool.

arguments

Tool-specific structured arguments.

The LLM may generate these arguments, but the application validates them.

Common Tool Result Envelope

Every tool should return:

{
"request_id": "uuid",
"tool_name": "query_metric",
"status": "success",
"data": {},
"warnings": [],
"error": null,
"provenance": {}
}

Status

Possible statuses include:

success
no_data
invalid_request
not_found
policy_rejected
timeout
provider_error
system_error

Data

Tool-specific successful result.

Warnings

Non-fatal conditions affecting interpretation.

Error

Structured error when execution is unsuccessful.

Provenance

Information required to trace the result to its source operation.

Structured Error Contract

Errors should use:

{
"code": "INVALID_TIME_RANGE",
"message": "end_time must be later than start_time",
"retryable": false,
"details": {}
}

Required Fields

code

Stable machine-readable code.

message

Human-readable explanation.

retryable

Whether bounded retry may be appropriate.

details

Structured diagnostics where safe.

Errors must not expose secrets, credentials, or unnecessary infrastructure details.

Tool 1: search_metric_descriptors

8.1 Purpose

Discovers available metric definitions relevant to an investigation.

It reduces reliance on the LLM remembering or inventing provider-specific metric names.

8.2 Request

{
"query": "request latency",
"project_id": "production-project",
"resource_type": "cloud_run_revision"
}

8.3 Fields

query

Semantic search text. Required.

project_id

Optional monitoring scope.

resource_type

Optional monitored-resource type.

Metric-label filters are not required for descriptor discovery in the initial contract. Metric-label constraints belong primarily to time-series querying once a concrete metric descriptor has been selected.

8.4 Response

{
"status": "success",
"data": {
"metrics": [
{
"metric_type": "example.googleapis.com/request_latency",
"description": "Request latency",
"unit": "ms",
"value_type": "DOUBLE",
"metric_kind": "GAUGE",
"labels": []
}
],
"result_metadata": {
"returned_count": 1,
"total_count_known": 1,
"truncated": false,
"transformed": false
}
}
}

8.5 Candidate Semantics

The tool returns candidate descriptors, not an authoritative answer.

A future implementation may expose deterministic ranking metadata such as match reasons or scores. The LLM may select among returned candidates, but the application remains authoritative for validation.

8.6 Validation

The application validates:

query length;

supported scope;

resource type;

result-size limits.

8.7 Selection Rule

The application validates that the selected metric exists and is compatible with the requested resource scope before query_metric() executes.

Tool 2: query_metric

9.1 Purpose

Retrieves time-series information within an explicit metric, resource, and temporal scope.

9.2 Request

{
"project_id": "production-project",
"metric": {
"type": "example.googleapis.com/request_latency",
"labels": {}
},
"resource": {
"type": "cloud_run_revision",
"labels": {
"service_name": "payments"
}
},
"interval": {
"start_time": "2026-08-27T00:00:00Z",
"end_time": "2026-08-28T00:00:00Z"
},
"aggregation": {
"alignment_period": "5m",
"per_series_aligner": "ALIGN_MEAN",
"cross_series_reducer": "REDUCE_NONE",
"group_by_fields": []
},
"query_preferences": {
"preferred_resolution": "5m"
}
}

The request expresses the caller's information needs and preferences. It must not expose application safety ceilings as LLM-controlled parameters.

9.3 Query Preferences

query_preferences may express preferences such as:

preferred_resolution
preferred_detail

These preferences never override application policy.

9.4 Metric Selector

MetricSelector
├── type
└── labels

type is required and must be a validated canonical metric type.

Metric-label filters are distinct from resource-label filters.
Every metric-label filter key must be defined by the selected MetricDescriptor.
An unknown metric-label key is an INVALID_REQUEST and must be rejected before provider execution.

9.5 Resource Selector

ResourceSelector
├── type
└── labels

For the initial contract, resource.type should be explicit.

If a preceding discovery step establishes the resource type unambiguously, the application may populate it before provider execution. The provider should not be responsible for guessing domain meaning from an underspecified request.

Project scope is represented separately by project_id.

9.6 Time Interval

The application must validate:

start_time < end_time

The configured maximum query interval must be enforced.

Relative user expressions are resolved by the application before provider execution.

9.7 Aggregation

The aggregation object may contain:

alignment_period
per_series_aligner
cross_series_reducer
group_by_fields

Alignment operates within individual series.

Cross-series reduction combines multiple aligned series.

When cross-series reduction is requested, the required alignment information must also be supplied.

Grouping specifies dimensions preserved before reduction.

Invalid combinations must be rejected.

query_metric Metric Selector

MetricSelector
├── type
└── labels

type

Required canonical metric type.

labels

Optional metric-label filters.

Metric-label filters must never be interpreted as resource-label filters.

query_metric Resource Selector

ResourceSelector
├── type
└── labels

type

Optional where the provider can infer it unambiguously.

labels

Optional monitored-resource-label filters.

Project scope is represented separately by project_id.

query_metric Time Interval

The application must validate:

start_time < end_time

The configured maximum query interval must be enforced.

Relative user expressions are resolved by the application before provider execution.

Example:

User:
"last 6 hours"

Application:
authoritative reference time
↓
resolved interval [T-6h, T]

The LLM does not become the authority for the actual timestamps used by the provider.

query_metric Aggregation

The aggregation object may contain:

alignment_period
per_series_aligner
cross_series_reducer
group_by_fields

13.1 Alignment

Alignment operates within individual time series.

raw points
↓
time buckets
↓
aligned series

13.2 Cross-Series Reduction

Reduction combines multiple aligned series.

VM-01 ─┐
VM-02 ─┼── REDUCE_MEAN → reduced series
VM-03 ─┘

13.3 Ordering Constraint

When cross-series reduction is requested, the required alignment information must also be supplied.

Invalid combinations must be rejected.

13.4 Grouping

Grouping specifies dimensions preserved before reduction.

The supported field set must be explicitly defined by the provider implementation.

query_metric Result-Size Policy

The application must bound returned results.

The query contract may express preferences such as:

preferred_resolution

The application independently enforces hard limits such as:

max_result_points
max_payload_size
max_query_interval

These hard limits are application policy, not LLM-controlled query parameters.

If the estimated result exceeds the safe bound, the application may:

apply a documented deterministic reduction;

select a coarser supported resolution;

return a structured warning/error;

require a narrower query.

The selected behavior must be visible in result metadata.

The system must not silently alter a query in a materially misleading way.

14.1 Truncation and Transformation Semantics

A bounded result must explicitly indicate whether it is complete.

Example:

{
"result_metadata": {
"returned_count": 100,
"total_count_known": 40000,
"truncated": true,
"transformed": true,
"transformation_summary": "5-minute alignment applied"
}
}

The LLM must never infer that returned records represent the complete population when truncated is true or when the provider reports incomplete pagination.

If additional data is available and the investigation needs it, the contract must provide a deterministic way to continue retrieval or issue a narrower query rather than relying on implicit assumptions.

query_metric Result

A successful result is conceptually:

{
"status": "success",
"data": {
"observations": [
{
"observation_id": "obs-001",
"metric": {
"type": "example.googleapis.com/request_latency",
"labels": {}
},
"resource": {
"type": "cloud_run_revision",
"labels": {
"service_name": "payments"
}
},
"statistic": "p95",
"value": 870,
"unit": "ms",
"interval": {
"start_time": "2026-08-27T14:00:00Z",
"end_time": "2026-08-27T14:05:00Z"
}
}
],
"summary": {
"series_count": 1,
"point_count": 1
},
"result_metadata": {
"returned_count": 1,
"total_count_known": 1,
"truncated": false,
"transformed": true,
"transformation_summary": "5-minute alignment applied"
}
},
"warnings": [],
"provenance": {}
}

Each investigation-facing observation or deterministic analysis exposed to the LLM must have a stable observation_id or analysis_id.

result_metadata is authoritative for whether the returned result is complete or transformed.

The LLM-facing result may contain bounded observations, deterministic analyses, or both.

Raw Provider Data vs LLM-Facing Result

The telemetry provider may return raw time-series data to the application.

The application transforms that result into an LLM-facing representation.

TelemetryProvider
↓
Provider Result
↓
Deterministic Result Processor
├── alignment
├── reduction
├── aggregation
├── comparison
├── trend analysis
└── bounded summarization
↓
Investigation Evidence
├── Observation IDs
└── Analysis IDs
↓
LLM-facing ToolResult

The provider result, investigation evidence, and LLM-facing result are conceptually distinct representations.

The application creates stable evidence identifiers after deterministic processing.

A ToolResult recorded in an investigation step represents the result actually exposed to the LLM. Raw provider data, when retained, should be referenced through provenance or a separate internal record rather than silently mutating the recorded ToolResult.

The same evidence identifier must continue to refer to the same semantic observation or analysis for the lifetime of the investigation.

Deterministic Result Summaries

Where meaningful for the metric, the application may derive:

minimum
maximum
mean
supported percentile
percentage change
trend direction
threshold crossings
temporal overlap
cross-series comparison

Example:

{
"summary": {
"min": 210,
"max": 920,
"mean": 610,
"p95": 870,
"trend": "increasing"
}
}

A statistic must only be calculated when meaningful for the metric semantics and sufficient data is available.

The system must not imply that every metric should receive the same statistical treatment.

Purpose

Retrieves monitored resources matching structured filters.

Request

{
"project_id": "production-project",
"resource_type": "gce_instance",
"labels": {
"environment": "production",
"service": "payments"
},
"limit": 100
}

Response

{
"status": "success",
"data": {
"resources": [
{
"resource_id": "vm-prod-01",
"type": "gce_instance",
"project_id": "production-project",
"labels": {
"environment": "production",
"service": "payments",
"zone": "asia-south2-a"
}
}
],
"result_metadata": {
"returned_count": 1,
"total_count_known": 1,

}

}

Validation

The application validates:

project scope;

resource type;

label structure;

maximum result size.

If provider pagination or result bounding occurs, result_metadata.truncated must accurately indicate that the response is incomplete.

Purpose

Retrieves alerts relevant to the investigation.

},
"interval": {

"end_time": "2026-08-28T00:00:00Z"
},
"severity": ["WARNING", "CRITICAL"]

{
"status": "success",
"data": {
"alerts": [
{
"alert_id": "alert-001",
"policy_reference": "high-cpu-policy",

Empty Results

An empty result is not an infrastructure failure.

Example:

{
"status": "no_data",
"data": {
"series": []
},
"warnings": [
"No observations matched the requested scope and time interval."
]
}

The system must distinguish:

NO_DATA
≠
METRIC_NOT_FOUND
≠
RESOURCE_NOT_FOUND
≠
INVALID_REQUEST
≠
PROVIDER_ERROR

Validation Pipeline

Validation occurs before provider execution.

ToolRequest
↓
Schema Validation
↓
Semantic Validation
↓
Policy Validation
↓
Provider Execution

Schema Validation

Checks:

required fields;

types;

enum values;

timestamp syntax;

structure.

Semantic Validation

Checks:

metric exists;

resource exists where required;

metric/resource combination is compatible;

start < end;

aggregation is valid;

alignment/reduction combination is valid;

requested preferences are supported.

Policy Validation

Checks:

maximum time range;

maximum result size;

maximum tool calls;

authorization;

allowed scopes;

concurrency limits.

Hard policy limits remain application-owned even when the LLM supplies preferences.

Only a request passing all applicable validation stages may reach the provider.

Tool Registry and Dispatch

The application should use an explicit registry:

Telemetry Tools
├── search_metric_descriptors → handler
├── query_metric              → handler
├── list_resources            → handler
└── get_alerts                → handler

Investigation Control
└── conclude_investigation    → handler

Unknown tools are rejected.

The registry must not dynamically execute:

class names supplied by the LLM;

arbitrary import paths;

shell commands;

SQL;

REST URLs;

code.

conclude_investigation() is an investigation-control action, not a telemetry retrieval tool.

The Controller remains responsible for deciding whether a conclusion request is valid and whether the investigation may transition to a terminal state.

Provenance Contract

Successful telemetry results must preserve enough provenance to trace the information used by the investigation.

At minimum:

provider
project/scope
metric scope
resource scope
query interval
aggregation parameters
retrieval timestamp

Provider-specific identifiers may be retained in infrastructure metadata.

Context Protection Contract

The application owns context protection.

The LLM may request:

preferred_resolution = 1m

but the application has final authority over whether that result is safe.

Example:

Requested:
1 month × 100 resources × 1 minute

Estimated:
4.32 billion points

Decision:
reject, coarsen, or require narrower scope

The LLM receives a structured result explaining the constraint.

Example:

{
"status": "policy_rejected",
"error": {
"code": "RESULT_SIZE_LIMIT",
"message": "Requested resolution would exceed the maximum allowed result size.",
"retryable": false,
"details": {
"suggested_resolution": "1h"
}
}
}

The LLM may decide how to continue the investigation, but it cannot override the policy.

A bounded or paginated result must not be treated as complete unless its result metadata says it is complete.

Duplicate and Repeated Requests

Repeated requests must not create an unbounded investigation loop.

The Controller should identify exact or materially identical requests within an investigation.

Initial behavior may be:

First request
→ execute

Repeated identical request
→ replay previous deterministic result where safe
OR execute again subject to limits

The exact replay/caching policy belongs in INVESTIGATION_LOGIC.md.

The first implementation should favor simple deterministic replay within the same investigation rather than introducing a distributed cache.

Retry Semantics

Retries belong to application/infrastructure code.

Typical behavior:

INVALID_REQUEST   → no retry
POLICY_REJECTED   → no retry
NOT_FOUND         → no retry
NO_DATA           → no retry
TIMEOUT           → bounded retry
PROVIDER_ERROR    → bounded retry if transient
SYSTEM_ERROR      → bounded retry where appropriate

The LLM does not determine low-level retry counts.

LLM Tool-Call Contract

The LLM must communicate through structured tool calls.

Conceptually:

{
"tool_name": "query_metric",
"arguments": {
"project_id": "...",
"metric": {},
"resource": {},
"interval": {},
"aggregation": {}
}
}

The LLM provider adapter converts provider-specific tool-call output into the internal ToolRequest.

Provider-specific wire formats do not leave the LLM integration boundary.

Tool 5: conclude_investigation

Purpose

Provides a structured terminal action through which the LLM submits its final findings and hypotheses for application/domain validation.

The tool does not retrieve telemetry.

Request

{
"findings": [
{
"statement": "Increased traffic coincided with CPU saturation and increased latency.",
"supporting_evidence": [
"obs-001",
"obs-002",
"analysis-003"
],
"status": "SUPPORTED"
}
],
"hypotheses": [
{
"statement": "The traffic increase contributed to CPU saturation.",
"supporting_evidence": [
"obs-002",
"analysis-003"
],
"contradicting_evidence": [],
"status": "UNRESOLVED"
}
],
"unresolved_questions": [
"Application logs were unavailable, so the underlying application error could not be verified."
]
}

Validation

Before accepting the conclusion, the application/domain validates:

every referenced evidence ID exists;

every referenced evidence item belongs to the current investigation;

the referenced evidence has not been invalidated;

findings have appropriate supporting evidence or deterministic analysis;

hypotheses are not represented as confirmed facts;

contradictory evidence is preserved;

the investigation has not already entered a terminal state.

Terminal Behavior

A valid conclude_investigation() request causes the Controller to transition the investigation into its terminal outcome flow.

The Controller, not the LLM, performs final persistence and lifecycle transition.

If evidence references are invalid, the conclusion request is rejected and the investigation may continue subject to normal limits.

Security Requirements for Tools

Tool contracts must prevent:

arbitrary SQL;

arbitrary API URLs;

arbitrary code execution;

credential access;

infrastructure mutation.

The LLM cannot supply:

database_connection_string
service_account_token
Authorization header
raw REST endpoint
shell command

as a mechanism for tool execution.

Contract Versioning

Tool contracts are internal APIs and should be versionable.

Conceptually:

contract_version = 1

Breaking changes must be explicit.

Provider implementations may evolve internally without changing the tool contract when observable semantics remain compatible.
