Data Model

GCP Observability Investigation Agent

Status: Design Draft
Derived From: PRD v0.8, DOMAIN_MODEL.md, SYSTEM_ARCHITECTURE.md, TOOL_CONTRACTS v0.3
Initial Storage: SQLite
Design Goal: Preserve domain semantics, integrity, traceability, and replaceability without overengineering the first implementation.

1. Purpose

This document defines the relational data model for the Phase 1 implementation.

It maps the domain concepts into SQLite while preserving:

metric/resource semantic separation;

time-series identity;

investigation lifecycle;

evidence traceability;

deterministic analysis provenance;

immutable investigation history;

auditability;

bounded-result metadata.

SQLite is an implementation choice for Phase 1.

The domain model remains independent of this schema.

2. Data Modeling Principles

2.1 Domain First

The database schema is derived from the domain model.

Database tables must not redefine domain semantics merely because a relational representation is convenient.

2.2 Normalize Stable Relationships

Relationships that require:

filtering;

joining;

referential integrity;

comparison;

indexing

should be represented relationally.

2.3 JSON Only for Variable Metadata

JSON may be used for:

provider-specific metadata;

flexible configuration details;

opaque diagnostic payloads where relational querying is not required.

Core identity and relationships should not be hidden entirely inside JSON.

2.4 Preserve GCP Semantics

Metric labels and monitored-resource labels are separate structures.

They must not be stored as one generic label collection.

2.5 Evidence Is Traceable

Every investigation-facing observation and deterministic analysis referenced by a finding must have a stable evidence identifier.

2.6 Historical Records Are Append-Oriented

Investigation steps, observations, analyses, and tool results represent historical events/evidence.

They should not be silently rewritten after recording.

3. Storage Domains

The schema is divided into two logical areas.

Telemetry
├── projects
├── metric_descriptors
├── metric_descriptor_labels
├── monitored_resources
├── resource_labels
├── metrics
├── time_series
├── data_points
└── alerts

Investigation
├── investigations
├── investigation_scopes
├── investigation_steps
├── tool_requests
├── tool_results
├── observations
├── deterministic_analyses
├── evidence_references
├── hypotheses
├── hypothesis_evidence
├── findings
├── finding_evidence
└── investigation_outcomes

The exact physical split into SQLite databases is not required.

These are logical domains within one schema.

4. Identifier Strategy

Use application-generated UUIDs for durable investigation-domain identifiers.

Examples:

investigation_id
step_id
request_id
result_id
observation_id
analysis_id
hypothesis_id
finding_id

Telemetry identity may use provider-shaped identifiers where necessary.

Evidence identifiers must be generated by the application and exposed to the LLM.

Recommended format:

obs-<unique-id>
analysis-<unique-id>

The exact UUID formatting can remain an implementation choice.

The important property is uniqueness and stable reference within the investigation.

5. SQLite Conventions

Unless otherwise required:

TEXT
INTEGER
REAL
BLOB

Timestamps should be stored as normalized UTC ISO-8601 strings or another consistently documented UTC representation.

Boolean values should use:

INTEGER
0 = false
1 = true

Foreign-key enforcement must be enabled:

PRAGMA foreign_keys = ON;

6. Telemetry Schema

6.1 projects

Represents monitoring project/scope.

projects
├── project_id            PK
├── display_name
├── created_at
└── metadata_json

Constraints

project_id is unique.

display_name may be null.

metadata_json is optional provider metadata.

7. Metric Descriptor Tables

7.1 metric_descriptors

Represents the definition and metadata of an available metric.

metric_descriptors
├── metric_type           PK
├── description
├── unit
├── value_type
├── metric_kind
├── metadata_json
└── created_at

Constraints

metric_type must uniquely identify a metric definition in the mock monitoring scope used by the application.

If future provider behavior requires project-specific descriptor identity, the key can be expanded without changing the conceptual model.

7.2 metric_descriptor_labels

Represents labels belonging to a metric descriptor.

metric_descriptor_labels
├── metric_type            FK
├── label_key
├── value_type
└── description

Primary key:

(metric_type, label_key)

This table stores descriptor metadata, not the label values for one particular time series.

8. Monitored Resource Tables

8.1 monitored_resources

Represents resources from which telemetry originates.

monitored_resources
├── resource_id            PK
├── project_id             FK
├── resource_type
├── display_name
├── metadata_json
└── created_at

Constraints

resource_id is unique.

project_id references projects.

resource_type is required.

8.2 resource_labels

Represents labels attached to a monitored resource.

resource_labels
├── resource_id             FK
├── label_key
└── label_value

Primary key:

(resource_id, label_key)

This allows queries such as:

environment = production
service = payments

without introducing a provider-specific filter language.

9. Metric Identity and Time-Series Tables

9.1 metrics

Represents a concrete metric identity used by a time series.

metrics
├── metric_id              PK
├── metric_type            FK
└── metadata_json

A metric type comes from metric_descriptors.

A concrete metric identity can carry additional provider-specific metadata if required.

9.2 time_series

Represents a fully identified metric/resource combination.

time_series
├── time_series_id         PK
├── metric_id              FK
├── resource_id            FK
├── metric_labels_json
├── created_at
└── metadata_json

Important Design Choice

Metric-label values are stored on the time-series identity because they define which particular time series is being represented.

For Phase 1, storing metric-label values as JSON is acceptable if the application does not need arbitrary SQL filtering over those values.

If metric-label filtering becomes a significant query requirement, a normalized child table can be introduced:

time_series_metric_labels
├── time_series_id
├── label_key
└── label_value

The domain semantics do not change.

Constraint

A time series is uniquely identified by:

metric identity
+
monitored resource
+
metric-label values

The exact uniqueness enforcement may use a canonicalized label representation or an internal identity hash.

10. Data Points

10.1 data_points

Stores individual time-series observations.

data_points
├── data_point_id         PK
├── time_series_id        FK
├── timestamp
├── value_type
├── numeric_value
├── string_value
├── boolean_value
├── distribution_json
└── interval_json

Only the value field corresponding to value_type should be populated.

The schema intentionally leaves room for more than one value representation because Cloud Monitoring metrics can have different value types.

Phase 1 should implement only the value types actually used by the mock scenarios.

10.2 Uniqueness

Where a metric representation guarantees one value per timestamp, an index should enforce or support:

(time_series_id, timestamp)

The exact uniqueness rule depends on whether interval-valued points are used.

11. Alerts

11.1 alerts

alerts
├── alert_id              PK
├── project_id            FK
├── policy_reference
├── condition_text
├── severity
├── status
├── start_time
├── end_time
├── resource_id           FK nullable
├── metric_id             FK nullable
├── metadata_json
└── created_at

Design Notes

resource_id and metric_id are optional.

An alert may be:

resource-associated;

metric-associated;

both;

associated through other policy/condition semantics.

This avoids forcing every alert into a metric-only structure.

12. Investigation Schema

12.1 investigations

The primary persisted investigation aggregate record.

investigations
├── investigation_id      PK
├── question
├── status
├── reference_time
├── timezone
├── created_at
├── started_at
├── completed_at
├── metadata_json
└── version

status

Candidate lifecycle values:

CREATED
RUNNING
COMPLETED
TERMINATED

Outcome/termination semantics are stored separately.

12.2 investigation_scopes

Represents the scope resolved for the investigation.

investigation_scopes
├── investigation_id      PK/FK
├── project_id            FK nullable
├── service
├── environment
├── resource_type
├── resource_id            FK nullable
└── metadata_json

A scope may specify broad or narrow selectors.

Additional selectors can be added through normalized relationships or structured metadata when justified.

12.3 investigation_outcomes

investigation_outcomes
├── investigation_id       PK/FK
├── outcome_status
├── termination_reason
├── response_summary
├── unresolved_questions_json
├── missing_evidence_json
└── persisted_at

Potential outcome_status values:

COMPLETED
PARTIAL
INSUFFICIENT_EVIDENCE
FAILED

Potential termination_reason values:

SUFFICIENT_EVIDENCE
MAX_TOOL_CALLS
MAX_DURATION
NO_NEW_EVIDENCE
TOOL_FAILURE
LLM_FAILURE
VALIDATION_FAILURE
SYSTEM_ERROR

Exact enums are finalized in INVESTIGATION_LOGIC.md.

13. Investigation Steps

13.1 investigation_steps

Represents ordered execution history.

investigation_steps
├── step_id               PK
├── investigation_id      FK
├── sequence_number
├── started_at
├── completed_at
├── execution_status
└── metadata_json

Unique constraint:

(investigation_id, sequence_number)

Sequence numbers must be monotonic within an investigation.

13.2 Immutability

Once a step has been completed or terminated, its historical request/result relationships should not be rewritten.

State fields may be finalized after execution.

14. Tool Requests

14.1 tool_requests

tool_requests
├── request_id            PK
├── step_id               FK
├── tool_name
├── contract_version
├── arguments_json
├── requested_at
└── validation_status

Validation Status

Examples:

PENDING
VALID
REJECTED

The raw LLM-generated arguments can be persisted as JSON for auditability.

The application must not execute them directly from storage.

15. Tool Results

15.1 tool_results

tool_results
├── result_id             PK
├── request_id            FK
├── status
├── data_json
├── warnings_json
├── error_json
├── provenance_json
├── result_metadata_json
└── recorded_at

Important Distinction

tool_results.data_json represents the tool result exposed to the LLM.

Raw provider responses, if retained, should live separately or be referenced through provenance.

The tool result must not be mutated after being recorded for an investigation step.

16. Raw Provider Result Storage

Raw provider results are optional in Phase 1.

If audit or debugging requirements justify retaining them:

provider_results
├── provider_result_id    PK
├── result_id             FK
├── provider_name
├── raw_payload_json
└── recorded_at

This table is not required for ordinary operation.

It should be introduced only if preserving raw provider payloads is useful enough to justify the storage cost and privacy/security implications.

17. Observations

17.1 observations

An observation is investigation-facing evidence derived from provider data.

observations
├── observation_id        PK
├── investigation_id      FK
├── step_id               FK
├── observation_type
├── metric_type           FK nullable
├── resource_id           FK nullable
├── time_series_id        FK nullable
├── statement
├── numeric_value
├── unit
├── interval_start
├── interval_end
├── source_metadata_json
└── created_at

The observation_id is the evidence identifier exposed to the LLM.

17.2 Provenance

An observation should identify the underlying source where possible:

metric_type
resource_id
time_series_id
step_id
interval

This allows a reviewer to trace:

Finding
 ↓
Observation
 ↓
Investigation Step
 ↓
Tool Result
 ↓
Telemetry Query

17.3 Immutability

Observation content and provenance should be append-only.

An invalid observation should be superseded or marked invalid rather than silently rewritten.

18. Deterministic Analyses

18.1 deterministic_analyses

deterministic_analyses
├── analysis_id          PK
├── investigation_id    FK
├── step_id              FK
├── operation
├── parameters_json
├── result_json
├── unit
├── created_at
└── provenance_json

Examples:

percentage_change
mean
max
p95
trend_direction
threshold_crossing
temporal_overlap
cross_series_comparison

The actual supported operations are defined in INVESTIGATION_LOGIC.md.

18.2 Reproducibility

The recorded input references and parameters must be sufficient to reproduce the analysis.

An analysis must not depend on an undocumented LLM calculation.

19. Evidence References

19.1 evidence_references

Provides a common evidence namespace for findings/hypotheses.

evidence_references
├── evidence_id          PK
├── investigation_id    FK
├── evidence_type
├── observation_id       FK nullable
├── analysis_id          FK nullable
└── created_at

Constraint

Exactly one of:

observation_id
analysis_id

should be populated.

This allows:

obs-001
analysis-003

to be treated uniformly by finding/hypothesis references.

The application generates evidence_id.

20.1 hypotheses

hypotheses
├── hypothesis_id        PK
├── investigation_id    FK
├── statement
├── status
├── support_level
├── confidence
├── created_at
└── updated_at

Potential status:

OPEN
SUPPORTED
WEAKENED

UNRESOLVED

Potential support level:

SUPPORTED
PARTIALLY_SUPPORTED
UNSUPPORTED

The exact semantics are finalized by INVESTIGATION_LOGIC.md.

20.2 hypothesis_evidence

hypothesis_evidence
├── hypothesis_id        FK
├── evidence_id          FK
├── relationship
└── created_at

relationship can distinguish:

SUPPORTING

Primary key:

(hypothesis_id, evidence_id, relationship)

21. Findings

21.1 findings

findings
├── finding_id           PK
├── investigation_id    FK
├── statement
├── status
├── support_level
├── confidence
├── created_at
└── updated_at

21.2 finding_evidence

finding_evidence
├── finding_id           FK
├── evidence_id          FK
├── relationship
└── created_at

Primary key:

(finding_id, evidence_id, relationship)

relationship may include:

SUPPORTING
CONTRADICTING

A finding should not be considered valid unless its evidence references pass application/domain validation.

22. Evidence Chain

The intended relational chain is:

Telemetry
   │
   ▼
TimeSeries
   │
   ├── DataPoints
   │
   ▼
ToolResult
   │
   ▼
Observation / DeterministicAnalysis
   │
   ▼
EvidenceReference
   │
   ├── Hypothesis
   └── Finding
        │
        ▼
   Investigation

For example:

finding-001
   ↓
evidence_id = obs-001
   ↓
observation-001
   ↓
step-004
   ↓
tool_result-004
   ↓
query_metric(request_latency)

This is the core auditability chain.

23. JSON vs Relational Decision

Relational

Use relational columns/tables for:

IDs;

foreign keys;

lifecycle state;

timestamps;

metric/resource identities;

investigation relationships;

evidence relationships;

values used for filtering or comparison;

ordered investigation steps.

JSON

Use JSON for:

provider-specific metadata;

raw tool arguments;

tool warnings;

error details;

flexible analysis parameters;

response summaries;

metadata not currently required for relational querying.

Avoid storing core evidence relationships solely inside JSON.

24. Indexing Strategy

Initial indexes should support actual investigation access patterns.

Telemetry

monitored_resources(project_id, resource_type)
resource_labels(label_key, label_value)

time_series(metric_id, resource_id)
data_points(time_series_id, timestamp)

alerts(project_id, start_time)
alerts(resource_id, start_time)

Additional indexes should be added only after observing real query patterns.

Investigation

investigation_steps(investigation_id, sequence_number)

tool_requests(step_id, requested_at)

tool_results(request_id)

observations(investigation_id, created_at)
observations(metric_type, resource_id, interval_start)

deterministic_analyses(investigation_id, created_at)

evidence_references(investigation_id)

hypotheses(investigation_id)
findings(investigation_id)

25. Referential Integrity

Foreign keys should be enabled.

Important relationships include:

resource → project
metric → metric_descriptor
time_series → metric
time_series → resource
data_point → time_series

investigation_step → investigation
tool_request → step
tool_result → request

observation → investigation
observation → step
observation → time_series

analysis → investigation
analysis → step

evidence_reference → investigation
evidence_reference → observation/analysis

hypothesis → investigation
hypothesis_evidence → hypothesis/evidence

finding → investigation
finding_evidence → finding/evidence

Deleting a parent investigation should not be used as the normal way to manage historical records.

The preferred behavior is retention and status-based lifecycle management.

26. Immutability Strategy

The following records should be treated as append-only historical facts:

InvestigationStep
ToolRequest
ToolResult
Observation
DeterministicAnalysis
EvidenceReference

Allowed changes should be limited to operational state fields where required during execution.

Once an investigation is terminal:

Investigation
   ↓
No new steps
No new observations
No new analyses
No new findings

The application should enforce this invariant.

27. Investigation Versioning

The investigations.version field supports optimistic consistency for persisted aggregate updates.

Initial implementation may use a simple integer:

1
2
3
...

The repository increments the version when mutable aggregate state is updated.

SQLite transaction boundaries must prevent lost updates.

The project should not introduce event sourcing merely for this purpose.

28. Transaction Boundaries

Important operations should be transactional.

Investigation creation

Persist:

investigation
+
scope

atomically.

Tool execution recording

Persist:

step
+
tool request
+
tool result
+
derived observations/analyses

within a consistent transaction where practical.

Conclusion

Persist:

findings
+
hypotheses
+
outcome
+
final investigation state

atomically before reporting terminal success.

If persistence fails, the application must not claim that the investigation completed successfully from an audit perspective.

29. Result Completeness Metadata

For bounded/paginated tool results, retain:

returned_count
total_count_known
truncated
transformed
transformation_summary

This metadata belongs to the tool-result record and must remain available when the investigation is reconstructed.

Example:

{
  "returned_count": 100,
  "total_count_known": 40000,
  "truncated": true,
  "transformed": true,
  "transformation_summary": "5-minute alignment applied"
}

30. Mock Telemetry Dataset Design

The mock dataset should be deterministic and scenario-driven.

Recommended scenario groups:

scenario_cpu_saturation
scenario_traffic_surge
scenario_memory_pressure
scenario_latency_without_cpu
scenario_error_spike
scenario_no_anomaly
scenario_missing_data
scenario_contradictory_evidence

Each scenario should identify:

projects
resources
metrics
time series
alerts
expected investigation findings

The scenario metadata should remain separate from the telemetry records where practical.

31. Mock Data Generation

Mock telemetry should be generated from deterministic seeds or checked-in fixtures.

The generator should be capable of producing:

stable timestamps;

predictable metric relationships;

known anomalies;

controlled missing data;

controlled contradictions.

The tests should not depend on random data that changes from run to run.

32. GCP Mapping Considerations

The SQLite schema is intentionally not a copy of the GCP API response structure.

Mapping conceptually:

GCP concept                 SQLite representation
----------------------------------------------------
Project                     projects
MetricDescriptor            metric_descriptors
Metric descriptor labels    metric_descriptor_labels
Monitored resource          monitored_resources
Resource labels             resource_labels
Metric identity             metrics
Time series                 time_series
Time-series points          data_points
Alert                       alerts

The GCP adapter is responsible for translating provider representations into this model.

The domain must not receive GCP SDK objects directly.

33. Migration Strategy

SQLite schema changes should use explicit migrations.

The initial project should maintain:

migrations/
├── 001_initial_schema.sql
├── 002_...
└── ...

Migration tooling can remain simple in Phase 1.

Schema changes must be versioned and reproducible from a clean database.

34. Backup and Portability Considerations

SQLite should remain easy to:

create from scratch;

back up;

inspect;

restore;

use in tests.

Production persistence may later move to PostgreSQL or another transactional store.

That migration should affect the persistence adapter and schema implementation rather than the domain model.

35. Data Retention

Phase 1 retention can be simple and configuration-driven.

Potential categories:

mock telemetry retention
investigation retention
audit retention

The schema should not require automatic deletion.

When retention policies are introduced, deletion behavior must account for audit requirements and evidence dependencies.

36. Data Integrity Rules

The following must always hold:

Metric labels ≠ resource labels

Every TimeSeries identifies a metric + resource

Every DataPoint belongs to one TimeSeries

Every Observation belongs to one Investigation

Every Observation has provenance

Every EvidenceReference belongs to its Investigation

Every Finding/Hypothesis evidence reference belongs to the same Investigation

Every deterministic Analysis is reproducible from recorded inputs/parameters

Every terminal Investigation has an Outcome

Every completed/terminated Investigation has a persisted audit trail

37. Database-to-Domain Mapping

The repository layer maps persistence records to domain objects.

Example:

SQLite rows
   ↓
Persistence models
   ↓
Domain entities/value objects

The repository should not simply return ORM/SQLite row objects as domain objects.

Similarly:

Domain entity
   ↓
Persistence mapper
   ↓
SQLite rows

This preserves the domain boundary.

38. What the Database Does Not Decide

The database must not decide:

whether a hypothesis is correct;

whether a finding is sufficiently supported;

whether an investigation should continue;

whether a tool should be executed;

whether a causal claim is justified;

how the LLM reasons.

These belong to application/domain logic.

The database enforces structural integrity, not semantic correctness of the investigation.
