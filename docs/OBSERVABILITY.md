GCP Observability Investigation Agent

Status: Design Draft
Derived From: PRD v0.8, DOMAIN_MODEL.md, SYSTEM_ARCHITECTURE.md, TOOL_CONTRACTS v0.3, DATA_MODEL.md, INVESTIGATION_LOGIC.md, AGENT_BEHAVIOUR v0.2, SECURITY_ARCHITECTURE.md, TESTING_STRATEGY.md, GCP_INTEGRATION v0.2
Purpose: Define how the agent itself is monitored, diagnosed, audited, and measured in development and production.

1. Purpose

This document defines the observability architecture for the application itself.

It covers:

structured logging;

investigation traces;

application metrics;

LLM telemetry;

tool telemetry;

persistence telemetry;

security-aware logging;

correlation identifiers;

investigation health;

cost/usage tracking;

operational dashboards;

alerts;

retention and sampling.

The system's observability must answer:

Is the service healthy?
Is the investigation engine behaving correctly?
Where is latency coming from?
Are tools failing?
Is the LLM behaving efficiently?
Are investigations completing successfully?
Are we approaching execution/cost limits?
Can a failed investigation be reconstructed?

2. Agent Observability vs Investigated Telemetry

Two telemetry domains must remain separate.

Investigated Telemetry
        ↓
GCP metrics / resources / alerts
        ↓
What the agent investigates

Agent Observability
        ↓
application logs / metrics / traces
        ↓
How the agent itself behaves

The agent's own observability must not accidentally become part of the user's investigated GCP data.

3. Observability Principles

3.1 Structured First

Logs and operational events should be machine-readable.

3.2 Correlatable

Every investigation should be traceable across:

request
investigation
step
tool call
provider call
LLM call
persistence

3.3 Minimal Sensitive Data

Do not log secrets or unnecessary raw telemetry.

3.4 High-Value Telemetry

Capture information useful for:

debugging;

reliability;

security;

performance;

cost control;

product evaluation.

3.5 Deterministic Correlation

Identifiers should be generated by the application rather than the LLM.

3.6 Operational vs Audit Separation

Operational logs answer:

"What is happening to the service?"

Audit records answer:

"What happened during this specific investigation?"

They may share identifiers but have different retention and content requirements.

4. Correlation Identifiers

The minimum identifiers are:

request_id
investigation_id
step_id
tool_request_id
tool_result_id
provider_request_id where available

Conceptual relationship:

request_id
   ↓
investigation_id
   ↓
step_id
   ↓
tool_request_id
   ↓
provider request

Every application log related to an investigation should carry the relevant IDs.

The LLM does not control these identifiers.

5. Logging Architecture

Structured logs should flow through:

Application / Adapter
        ↓
Structured Logger
        ↓
Redaction
        ↓
Log Sink

The logger must apply security-sensitive redaction before emitting records where practical.

6. Investigation Logging

For each investigation, operational logs should be sufficient to identify:

investigation started
investigation completed
investigation terminated
tool requested
tool validated
tool executed
tool failed
evidence created
hypothesis updated
conclusion attempted
conclusion accepted/rejected
persistence succeeded/failed

The complete audit record remains in the repository.

Operational logs should not duplicate full telemetry payloads merely for convenience.

7. Tool-Call Logging

Every tool execution should emit structured telemetry with fields such as:

investigation_id
step_id
tool_request_id
tool_name
validation_status
execution_status
duration_ms
retry_count
result_size
truncated
transformed
error_code

Arguments may be logged in sanitized form when useful.

Secrets and unnecessary high-cardinality telemetry values must not be logged.

8. LLM Call Logging

Each LLM invocation should capture operational metadata such as:

investigation_id
step_id
provider
model
duration_ms
request_size / estimated tokens
input token usage where available
output token usage where available
total token usage where available
finish status
tool-call requested
error category
retry count

The system should not automatically log full prompts or full LLM responses.

If prompt/response capture is needed for controlled debugging, it must be explicitly configured, redacted, access-controlled, and treated as sensitive data.

9. LLM Cost Tracking

Where the provider supplies usage information, record:

input_tokens
output_tokens
total_tokens
cached/input-cached tokens where available
provider-reported cost where available

At minimum, cost should be attributable to:

investigation_id
LLM provider
model

The system should be able to answer:

Which investigations consumed the most model usage?
Which model is most expensive?
What is the average model cost per investigation?

Provider pricing calculations should remain outside the domain model.

They belong to operational telemetry/configuration.

10. Tool Latency

Track latency separately for:

LLM call
metric discovery
metric query
resource discovery
alert retrieval
persistence

Useful metrics include:

count
success count
failure count
p50
p95
p99

A single end-to-end latency metric is not sufficient to identify where time is being spent.

11. Investigation Metrics

The application should expose metrics such as:

investigations_started_total
investigations_completed_total
investigations_partial_total
investigations_insufficient_evidence_total
investigations_failed_total

investigation_duration_seconds

tool_calls_total
tool_call_failures_total
tool_call_retries_total

llm_calls_total
llm_failures_total

observations_created_total
hypotheses_created_total
findings_created_total

conclusions_rejected_total

These metrics should support operational trend analysis.

12. Investigation Success Metrics

Operationally, an investigation should not be considered successful merely because the process reached COMPLETED.

Track multiple dimensions:

lifecycle outcome
evidence sufficiency
tool efficiency
failure rate
unsupported-claim rate
user-visible completion

This allows:

technical success
≠
investigation quality

Quality evaluation remains primarily part of the testing/evaluation system.

13. Investigation Outcome Distribution

The system should monitor the distribution of:

COMPLETED
PARTIAL
INSUFFICIENT_EVIDENCE
FAILED

A sudden increase in:

FAILED

may indicate infrastructure/provider problems.

A sudden increase in:

INSUFFICIENT_EVIDENCE

may indicate:

incomplete telemetry coverage;

metric discovery problems;

overly restrictive tool limits;

poor agent planning.

14. Tool Efficiency Metrics

Track:

average actions per investigation
median actions per investigation
p95 actions per investigation
average repeated requests
average retries

The goal is not to minimize all tool calls.

The goal is to identify:

unnecessary calls
loops
expensive investigations

15. Investigation Budget Metrics

Track usage against configured limits:

actions_used
action_limit

duration_used
duration_limit

result_size
result_size_limit

This helps detect investigations that frequently terminate because they hit policy boundaries.

16. Context Metrics

Where measurable, track:

context size
estimated input tokens
estimated output tokens
number of observations included
number of analyses included
number of hypotheses included
number of tool results included
context pruning events

Do not log full context contents by default.

17. Persistence Metrics

Track:

repository_read_total
repository_write_total
repository_read_latency
repository_write_latency
repository_errors_total
transaction_rollbacks_total

For terminal investigations, monitor:

terminal_persistence_failures_total

A terminal result must not be reported as successfully persisted when the repository write failed.

18. Security Metrics

Track security-relevant events without exposing sensitive data.

Examples:

authorization_denied_total
policy_rejections_total
invalid_evidence_reference_total
invalid_tool_request_total
prompt_injection_detected_total where detection exists
oversized_request_total
oversized_provider_response_total

These metrics should help identify attacks and integration problems.

19. Provider Health Metrics

The system should expose provider-specific health telemetry for:

LLM
GCP Monitoring
Persistence

Useful metrics:

request count
success count
failure count
timeout count
retry count
latency

Provider labels should have bounded cardinality.

Do not use arbitrary user/project/resource names as metric label values unless there is a demonstrated need.

20. Tracing Model

If distributed tracing is introduced, the logical span model should resemble:

Investigation
   ├── Context Build
   ├── LLM Call
   │    └── Tool Decision
   ├── Tool Call
   │    └── Provider Call
   ├── Deterministic Processing
   ├── Evidence Creation
   ├── Conclusion Validation
   └── Persistence

The system should support tracing without making tracing infrastructure a domain dependency.

21. Span Attributes

Useful trace attributes include:

investigation_id
step_id
tool_name
provider
model
status
duration_ms
retry_count
result_size
truncated
transformed

Do not put:

credentials
raw prompts
full telemetry
secrets

into span attributes by default.

22. Sampling

Tracing and detailed operational telemetry may be sampled.

Recommended principle:

100% of important failure events
+
100% of audit records
+
sampled successful detailed traces

Audit records are not subject to ordinary trace sampling.

A completed/terminated investigation must retain its audit record even when distributed tracing samples out the request.

23. Error Taxonomy for Observability

Metrics and logs should categorize failures consistently.

Example categories:

VALIDATION_ERROR
AUTHORIZATION_ERROR
POLICY_ERROR
LLM_ERROR
TELEMETRY_ERROR
PERSISTENCE_ERROR
TIMEOUT
SYSTEM_ERROR

The exact error codes remain aligned with the tool contracts.

24. Operational Logging Levels

Use levels consistently:

DEBUG
INFO
WARNING
ERROR
CRITICAL

Example:

INFO:
investigation started

DEBUG:
tool request normalized

WARNING:
tool result truncated

ERROR:
GCP provider timeout

CRITICAL:
persistence unavailable for terminal investigation

DEBUG logging should not be enabled broadly in production if it could expose sensitive data.

25. Redaction Policy

The logging layer should redact or exclude:

API keys
access tokens
passwords
private keys
authorization headers
session secrets
database credentials

Potentially sensitive telemetry should also be minimized.

Resource labels may themselves contain sensitive values and should not automatically become unrestricted log fields.

26. Prompt/Response Capture

Full LLM prompts and responses are useful for debugging but can contain:

user questions;

telemetry;

resource identifiers;

internal system instructions;

sensitive operational data.

Therefore full capture should be:

disabled by default
OR
explicitly enabled
+
redacted
+
access controlled
+
retained briefly

Structured investigation state and audit records remain the preferred debugging source.

27. Health Checks

The application should expose a basic health mechanism.

Conceptually:

/health

should indicate whether the application process is responsive.

A separate readiness check may verify required dependencies:

/ready

Potential readiness dependencies:

persistence
required configuration
LLM provider availability where appropriate
GCP provider connectivity where appropriate

Health checks should not execute expensive investigations.

28. Startup Diagnostics

At startup, log safe configuration diagnostics such as:

application version
environment
configured provider names
configured feature flags
configured limits
database initialization status

Do not log:

API keys
credential contents
secret values

30. Operational Alerts

Potential alerts include:

high investigation failure rate
high LLM provider failure rate
high GCP provider failure rate
high persistence error rate
sustained investigation latency
sudden token/cost increase
unusual tool-call volume
authorization failure spike

Alerts must be based on meaningful thresholds rather than every isolated error.

31. Service-Level Indicators

Potential SLIs:

Investigation availability
Investigation completion rate
Successful terminal persistence rate
Median investigation latency
P95 investigation latency
LLM success rate
Telemetry success rate

These should be measured separately from the correctness/quality metrics used in agent evaluation.

32. Service-Level Objectives

Initial targets should be established only after baseline performance is measured.

Avoid declaring arbitrary production SLO percentages before the system has real operating data.

The design should support configurable targets such as:

successful investigation completion
terminal persistence success
P95 latency
provider availability

The actual numbers belong in deployment operations once real usage exists.

33. High-Cardinality Protection

Operational metrics must avoid unbounded labels such as:

investigation_id
request_id
user_question
resource_id
arbitrary metric name

These values belong in logs/traces where appropriate, not automatically in metric dimensions.

Metrics should use low-cardinality labels such as:

provider
tool_name
status
error_category
model

34. Audit vs Operational Telemetry

The system should maintain:

Audit Record
    ↓
complete investigation reconstruction

Operational Logs
    ↓
debugging / service health

Metrics
    ↓
aggregation / alerting

Traces
    ↓
latency / dependency analysis

No single mechanism should be expected to perform all four jobs.

35. Development Observability

During Phase 1, keep the stack simple.

At minimum:

structured application logs
basic counters/timers
investigation IDs
tool-call tracing through logs
SQLite persistence visibility
LLM usage logging where available

A full distributed tracing platform is not required merely because the architecture mentions traces.

36. Production Evolution

As deployment grows, the observability stack can evolve toward:

Application
   ↓
OpenTelemetry-compatible instrumentation
   ↓
logs / metrics / traces backend
   ↓
dashboards / alerts

The application should avoid vendor-locking the domain to a specific observability platform.

37. Testing Observability

Observability itself should be tested.

Verify that:

investigation IDs propagate
tool-call events contain correct IDs
errors emit expected categories
secret fields are redacted
terminal persistence failures are visible
metrics increment correctly
truncated results are observable
authorization failures are recorded

Test logs for the absence of known secret fixtures.

38. Failure-Path Observability

Every major failure should leave enough telemetry to answer:

What failed?
Where?
When?
For which investigation?
After how many steps?
Which provider was involved?
Was retry attempted?
Was evidence preserved?
Was terminal state persisted?

The system should avoid logging sensitive payloads simply to make failure diagnosis easier.

39. Cost Guardrails

The system should monitor:

tokens per investigation
LLM calls per investigation
tool calls per investigation
estimated cost per investigation
daily/periodic total cost

The application should be capable of enforcing configured usage limits independently from monitoring them.

Observability detects cost problems.

Application policy prevents runaway usage.

40. Investigation-Level Debugging View

A useful internal debugging view should be able to show:

Investigation ID
Question
Start / end
Status
Termination reason

Timeline
├── Step 1
│   ├── tool
│   ├── duration
│   └── result
├── Step 2
│   ├── tool
│   ├── duration
│   └── result
└── Conclusion

Evidence
├── observations
├── deterministic analyses
├── hypotheses
└── findings

Provider usage
├── LLM
├── GCP
└── persistence

This view should use persisted structured state and operational telemetry rather than reconstructing history from arbitrary prompt text.

41. Observability Invariants

The following should always hold:

Every investigation has a correlation ID.

Every tool action is attributable to an investigation step.

Every terminal investigation has a durable audit record.

Secrets do not appear in operational logs.

Raw telemetry is not logged indiscriminately.

Provider failures are observable.

LLM usage is measurable where the provider exposes it.

Hard limits remain enforceable even if observability fails.

The final rule is especially important:

Observability must never become a prerequisite for enforcing safety.

If metrics/logging fail, the application must still enforce:

authorization;

tool limits;

result-size limits;

evidence validation;

terminal-state rules.

42. Final Observability Model

                     Investigation
                           │
                 ┌─────────┴─────────┐
                 ▼                   ▼
           Audit Record        Operational Events
                 │                   │
                 │             ┌─────┼─────┐
                 │             ▼     ▼     ▼
                 │           Logs  Metrics Traces
                 │             │     │     │
                 └─────────────┴─────┴─────┘
                               │
                               ▼
                      Operational View

Underlying dependency telemetry:

Investigation
   ├── LLM
   ├── GCP
   └── Persistence

The observability design allows operators to move from:

"What is failing?"
        ↓
"Which investigation?"
        ↓
"Which step?"
        ↓
"Which provider?"
        ↓
"What happened?"

without requiring unrestricted raw data capture.

43. Final Design Principles

Observe the system without trusting the system to observe itself.

Log structured events, not indiscriminate payloads.

Measure latency by dependency, not only end-to-end.

Track model usage and cost explicitly.

Keep audit records complete even when traces are sampled.

Keep operational metrics low-cardinality.

Redact secrets before emission.

Do not make observability a security dependency.

Prefer simple instrumentation in Phase 1.

Introduce distributed telemetry infrastructure when actual operational requirements justify it.
